## Architecture

EduGraph AI is a curriculum-intelligence platform for Ethiopian K-12 education. **What actually runs today is a local-dev Docker Compose stack for everything except Postgres** — Postgres moved to a hosted Supabase project on 2026-08-10 (see "Postgres is now Supabase" below); this is still not the national-scale production system described in `EduGraph AI/edugraph-architecture.docx` (see "Planning docs vs. reality" below).

Services (`docker-compose.yml`):
- **`api`** — Go 1.22+ monolith (chi router, manual DI, no framework). Port 8080.
- **`ai-service`** — Python 3.12 FastAPI service. Port 8000. Runs **eight** background workers in the same process as asyncio lifespan tasks (see below) — seven Redis-queue (`BRPOP`) consumers plus one time-based nightly worker (EG-GCKT's `refit_worker.py`, 2026-08-15, the first non-queue-driven one) — plus **one** real HTTP route (`/api/v1/tutor/ask`).
- **`frontend`** — React 18 + TypeScript + Vite (TanStack Router/Query, Zustand, Tailwind, Radix), served by the Vite dev server in dev. Port 5173. Role-based dashboards for all six roles now exist (see "Frontend" below) — this was empty scaffolding until 2026-07-17.
- **`postgres`** — **local fallback only, not started by default** (`profiles: ["local-db"]`) — see "Postgres is now Supabase" below. System of record either way. pgvector is in real use now for CLO/topic embeddings — see 2026-08-10 entries below.
- **`neo4j`** — Curriculum + student-progress knowledge graph (`Subject→Unit→Topic`, `HAS_PREREQUISITE`, `School→Student→STRUGGLED_WITH→Topic`). Still local Docker, deliberately not moved to a hosted graph DB.
- **`redis`** — Job queue between `api` and `ai-service` (five queues, all plain-string `LPUSH`/`BRPOP`, see below), plus refresh-token storage.
- **`ollama`** — **is load-bearing** (`app/utils/llm_provider.py`'s `LLMProvider` adapter, same shape as `pkg/storage.StorageProvider`/`embeddings.py`'s `EmbeddingProvider`): `LLM_PROVIDER` defaults to `local`, meaning gap-analysis explanations, the AI tutor, study-plan day goals, and the exam-to-CLO LLM matcher all call Ollama by default, with Gemini as the configured fallback (`generate_with_fallback`) tried only if the primary is unset/unreachable — not the other way around. `OLLAMA_MODEL` defaults to `qwen2.5:7b-instruct-q4_K_M` (verified against real local models: `qwen2.5:7b-instruct`/`gemma2:9b` both produce broken Amharic, so `LLMProvider.supports_amharic` is `False` for Ollama and call sites must request English-only). The container's own named volume starts with zero models pulled — `docker compose exec ollama ollama pull qwen2.5:7b-instruct-q4_K_M` works but re-downloads ~4.4GB; to reuse an existing local Ollama install's models instead, bind-mount its models directory over `/root/.ollama/models` in a gitignored `docker-compose.override.yml` (Compose loads it automatically) rather than editing the shared `docker-compose.yml` with a machine-specific host path.
- **`jaeger`**, **`prometheus`**, **`grafana`** — present in compose but not load-bearing for any pipeline; optional/observability.

### Postgres is now Supabase (2026-08-10)

`docker compose up -d` (no profile) **no longer starts a local Postgres container** — `api`/`ai-service` connect to a hosted Supabase project instead, configured entirely through `.env`. This wasn't a like-for-like swap; two things had to change to make it work:

- **Must use the session pooler, not the direct connection.** Supabase's direct-connect host (`db.<ref>.supabase.co:5432`) is IPv6-only; most networks (including the one this was built on) have no outbound IPv6 route and can't resolve/reach it at all. `POSTGRES_HOST` is the pooler host instead (`aws-0-<region>.pooler.supabase.com:5432`, session mode — not the 6543 transaction-mode pooler, which doesn't support the server-side prepared statements pgx and asyncpg both use by default). `POSTGRES_USER` is correspondingly `postgres.<project-ref>`, not plain `postgres`.
- **`storage` is a Supabase-owned schema name, `app_storage` is ours.** Every Supabase project provisions its own Storage product into a `storage` schema (buckets/objects/etc, owned by `supabase_admin`) before any app migration ever runs; the `postgres` role has USAGE but not CREATE there. Migration V013 (`create_local_storage`) was edited in place to target `app_storage.local_files` instead of `storage.local_files` — the one exception to "never edit a merged migration" in this repo, made because V013 had never successfully applied anywhere (it fails identically on every fresh Supabase project) and Postgres DDL is transactional, so the failed attempt left no trace to reconcile. `backend/pkg/storage/postgres.go` and `ai-service/app/db/postgres.py` were updated to match.
- **`POSTGRES_SSLMODE`** is a new config knob (`pkg/config/config.go`, `ai-service/app/core/config.py`) — Supabase requires `require`; the local-fallback `postgres` container still works with the old implicit `disable`.
- **`PostgresConfig.DSN()`/`Settings.POSTGRES_DSN`** now percent-encode the user/password instead of raw string-formatting them into the connection URL — Supabase-generated passwords routinely contain `@`/`?`/`&`, which break naive DSN construction (this was caught and fixed during the migration, not a pre-existing bug that shipped).
- **`POSTGRES_MAX_CONNS`** dropped from 80 to 15 in `.env` — the pooler's connection budget is shared across everything hitting the project, not sized per-app the way a dedicated local container's was.

Local fallback (offline dev, or if Supabase is unreachable): `docker compose --profile local-db up -d postgres flyway`, then set `POSTGRES_HOST=postgres`, `POSTGRES_USER=edugraph`, `POSTGRES_DB=edugraph`, `POSTGRES_SSLMODE=disable` in `.env`.

Backend structure: `internal/<domain>/{handler,service,repository,dto}` per domain (auth, curriculum, assessment, career, student, teacher, school, region, ministry, sync, notification, jobs, storage). `pkg/` holds cross-cutting infra (crypto, storage, middleware, database clients, config, errors, validator, `ai` — the Go→ai-service HTTP client).

AI service: **not Celery** despite what `requirements.txt` and older docs imply — every worker but one is a plain `asyncio` loop doing Redis `BRPOP` on its own queue, all started together as FastAPI lifespan background tasks (`app/main.py`, `WORKERS` tuple). The one exception is EG-GCKT's `refit_worker.py` (2026-08-15), a time-based `asyncio` periodic loop (mirrors the Go `qualityworker` ticker pattern) — still no Celery, just not queue-triggered, since "refit whenever enough evidence has accumulated" has no single triggering event. Rationale documented in `app/workers/curriculum_worker.py`: the Go side does a raw `LPUSH` of a job-id string, not a Celery-protocol message, so a Celery consumer doesn't apply. The five queues (`app/db/redis.py`): `queue:curriculum:parse`, `queue:exam:parse`, `queue:exam:answerkey`, `queue:gap:analyze`, `queue:studyplan:generate`. **Deliberate dev-mode assumption** (stated in `main.py`'s lifespan docstring): in production each worker would likely run as its own container/process so parsing load doesn't compete with request handling, but running all five in-process keeps local Docker Compose simple since only one `ai-service` container is defined.

## Key Components — The Curriculum Pipeline (Phase 1)

The core feature, defined in `EduGraph AI/Untitled document.docx` ("Improvised Implementation of Phase 1"), is a 4-step pipeline built around a **dual-storage adapter pattern** so the system runs locally without AWS and can swap to S3 later with zero handler/service changes:

```go
// backend/pkg/storage/interface.go
type StorageProvider interface {
    Upload(ctx, fileName, mimeType string, file io.Reader) (ref string, error)
    Download(ctx, ref string) (io.ReadCloser, error)
}
```
Dev implementation: `PostgresStorage` (`backend/pkg/storage/postgres.go`) — stores file bytes in `storage.local_files` (BYTEA), returns the row UUID as the reference. No `S3StorageProvider` exists yet (prod-mode is not implemented, by design).

1. **Upload** (`POST /api/v1/curriculum/upload`, `curriculum` handler/service) — role-gated to `curriculum_officer`/`ministry_admin`, magic-byte validated (not `Content-Type` header — see Critical Decisions), saved via `StorageProvider`, `curriculum.upload_jobs` row created, job id pushed to Redis.
2. **Parse** (`ai-service` curriculum worker) — `BRPOP`s the queue, fetches bytes via the same dual-storage abstraction (`app/db/postgres.py:fetch_file_bytes`), runs PyMuPDF-based extraction (`app/services/curriculum_parser/extractor.py` for PDF, `docx_extractor.py` for DOCX) using a TOC-first / font-heuristic-fallback strategy, writes `parsed_structure` JSONB and flips status to `parsed`.
3. **Human review** (`GET /api/v1/curriculum/jobs/{id}`, `GET /api/v1/storage/files/{jobId}` proxy, `POST /api/v1/curriculum/jobs/{id}/approve`) — frontend (`frontend/src/features/curriculum/JobReviewPage.tsx`) renders an editable unit/topic tree, lets the officer view the original file via a blob-fetch (not a plain `<a href>`, since the proxy endpoint needs a Bearer token a browser can't attach to a navigation), and submits edits or approves as-is.
4. **Finalize** (`ApproveAndPromote` in `backend/internal/curriculum/repository/repository.go`) — one Postgres transaction upserts `curriculum.subjects/units/topics/clos` (and, as of 2026-08-10, subtopics via `curriculum.topics.parent_topic_id` and unit-level CLOs fanned out to every topic in the unit — see "Topic hierarchy + CLO graph sync" below), then (outside the transaction, best-effort) mirrors Subject→Unit→Topic→CLO into Neo4j via `MERGE`. CLO nodes **are now mirrored to Neo4j** (`(:Topic)-[:HAS_CLO]->(:CLO)`) — the Phase 2 deferral noted in earlier versions of this doc is resolved; only `edugraph-impl-plan.docx` Capability 1C's exact original design is what was skipped, not CLO graph sync itself.

## What's Built — CLO/Topic Embeddings, Officer Dashboard, Curriculum Versioning (2026-08-10)

- **CLO/topic vector embeddings** (migration V025, `queue:embedding:generate`) — `ApproveAndPromote` (`curriculum/repository/repository.go`) now collects an `EmbeddingTarget` for every topic and distinct CLO it promotes and `Service.Approve` LPushes one small JSON job (`{"kind":"topic","id":...}` / `{"kind":"clo","code":...}`) per target. `ai-service/app/workers/embed_worker.py` BRPOPs the queue, re-fetches the current title/description from Postgres (`app/db/pgvector.py`), and upserts into `embeddings.clo_embeddings` / the new `embeddings.topic_embeddings` table. **No real embedding model is wired up yet** — `app/utils/embeddings.py` defines a pluggable `EmbeddingProvider` interface (mirrors the `StorageProvider` adapter pattern) but `get_embedding_provider()` always returns `StubEmbeddingProvider`, a deterministic hash-based 768-dim placeholder (`model_ver = "stub-hash-v1"`). Cosine similarity between stub vectors is **not semantically meaningful** — swapping in a real model (Gemini embeddings API vs. local via Ollama, still undecided) is the one remaining piece before semantic exam-compliance matching (PRD §5.1) can work.
- **Curriculum Officer dashboard** (`GET /api/v1/curriculum/jobs`, `CurriculumDashboardPage.tsx`) — paginated list of the caller's own upload jobs (status, subject/grade/year, submitted/approved dates), linking into the existing `JobReviewPage`. `landingPathFor('curriculum_officer')` now points at `/curriculum` instead of straight to `/curriculum/upload`; `/curriculum/upload` still exists and is reachable from the dashboard's "Upload curriculum" button and the sidebar.
- **Curriculum revision/versioning** (migration V025, `curriculum/{dto,repository,service,handler}/versions.go`) — decision made: a mid-year revision is promoted under a **new** subject code through the normal upload/approve pipeline (unchanged), then explicitly linked via `POST /api/v1/curriculum/subjects/{newCode}/supersede` (body `{"previousCode": "..."}`), which flips the old subject's `is_current=false`/`superseded_at=now()` and sets the new one's `version`/`previous_version_code`/`is_current=true`. `GET /api/v1/curriculum/subjects/{code}/versions` walks the lineage oldest-first. Deliberately does **not** touch `ApproveAndPromote`'s existing upsert-by-natural-key behavior (re-approving the *same* job still updates in place, which is correct — only cross-version linking is new) and never copies/mutates units/topics/clos, so `gap_records`/`study_plans`/`questions` pointing at an old version's `topic_id`/`clo_code` keep meaning exactly what they meant when written.
- **Prerequisite links: validated vs. inferred, plus Postgres → Neo4j resync** (migration V026, `curriculum/{dto,repository,service,handler}/prerequisites.go`) — `AddTopicPrerequisite` now takes `inferMethod`: human-authored provenance (`manual`/`explicit`/`moe_document`, the default) is confirmed immediately (`reviewed_by`/`confirmed_at` set), `ai_inferred` is left unconfirmed (`IsValidated: false` in the response) until a separate `PATCH /api/v1/curriculum/topics/{id}/prerequisites/{prereqId}/validate` call confirms it. `curriculum.topic_prerequisites` gained a `neo4j_written` column (every *other* best-effort-synced table already had one — this was the one write path with no way to detect or retry a failed sync); `POST /api/v1/curriculum/prerequisites/resync` (ministry_admin only) re-mirrors every row where `neo4j_written = false` and reports `{synced, failed}` — the actual fix for "prerequisite links weren't reliably mirrored," since the per-request best-effort sync at creation time already existed but had no backstop. Frontend added 2026-08-11 — see below.
- **Topic hierarchy (subtopics) + CLO graph sync** (migration V027, `curriculum/repository/repository.go`) — `curriculum.topics` gained a self-referencing `parent_topic_id` (NULL for top-level topics); a subtopic is promoted as its own `topics` row like any other (independently gap-analyzable/exam-alignable), not a separate type. `dto.ParsedTopic` gained recursive `Subtopics` and an `ExternalCode` field (opaque, caller-only, never written to Postgres — lets a bulk importer resolve its own source-document topic IDs back to generated UUIDs post-promotion via the new `Repository.PromotionResult.TopicIDByCode`). `dto.ParsedUnit` gained `UnitClos` for CLOs stated at unit level rather than tied to one topic (a syllabus's "Unit Outcomes" list) — each one is mapped via `topic_clo_mappings` to *every* topic and subtopic in that unit (`match_method='manual'`, vs. `'human_confirmed'` for a direct topic-CLO pairing), so it stays queryable through the same topic-driven paths (gap analysis, exam alignment) everything else uses. `syncCurriculumGraph` now also mirrors `(:Topic)-[:HAS_SUBTOPIC]->(:Topic)` and `(:Topic)-[:HAS_CLO]->(:CLO)` for every topic (closing the "CLO Neo4j sync deferred" gap noted elsewhere in this doc, for the topics/CLOs this code path actually touches).
- **Frontend for prerequisites + versioning** (2026-08-11, `frontend/src/features/curriculum/{PrerequisitesPage,CurriculumVersionsPage}.tsx`) — the only new frontend surfaces for everything built 2026-08-10 (embeddings/dashboard/versioning backend/prerequisite-validation backend all shipped without UI at the time). `PrerequisitesPage` (`/curriculum/prerequisites`): enter a subject code → topic picker (subtopics indented under their parent) → view/add/validate that topic's prerequisite links, plus a ministry_admin-only "Resync to Neo4j" panel. `CurriculumVersionsPage` (`/curriculum/versions`): view a subject's version lineage, link a new version as superseding an old one. Both gated the same as the rest of curriculum (`requireCurriculumAccess`, curriculum_officer/ministry_admin), reachable from their sidebar nav. Required one small **new backend endpoint**: `GET /api/v1/curriculum/subjects/{code}/topics` (`dto.TopicListItem`, `curriculum/{dto,repository,service,handler}/topic_list.go`) — no endpoint existed to resolve a topic's UUID at all (the prerequisite endpoints all take a topic ID the frontend had no way to discover), so this is a flat, subject-scoped list purpose-built for that picker, not a general "browse the curriculum" API (that was explicitly scoped out). Verified against real data in a real browser (Playwright, not just build/lint) against the live Biology dataset: loaded BIO-G9's 106 topics, viewed "The Cell"'s 2 real `moe_document` prerequisites, added and validated a test `ai_inferred` link end-to-end (then removed it from both Postgres and Neo4j afterward so the real dataset stayed exactly 90 edges), and confirmed a subject's version lineage renders correctly.
- **Neo4j graph visualization** (2026-08-11, `curriculum/{dto,repository,service,handler}/graph.go`, `frontend/src/features/curriculum/CurriculumGraphPage.tsx`) — `GET /api/v1/curriculum/subjects/{code}/graph?includeClos=true` queries Neo4j directly (not Postgres) for a subject's Subject→Unit→Topic[→Subtopic][→CLO] subtree plus every `HAS_PREREQUISITE` edge touching one of those topics, including the topic at the *other* end when it belongs to a different subject (cross-grade prerequisites are the norm, not the exception, in the Biology dataset) -- rendered as a minimal dashed "external" node (`{"...", "gradeLevel": N, "subjectCode": "BIO-GN", "external": true}`) rather than silently dropped or expanded into its own full subtree. CLOs are opt-in (`includeClos`, default false) since a subject's CLO count can be several times its topic count. Frontend: `/curriculum/subjects/{code}/graph`, reached via a "View knowledge graph" button on `JobReviewPage` (approved jobs) and a "Graph" action per approved row on `CurriculumDashboardPage`. Renders with `reactflow` + `dagre` (new deps -- neither library does both layout and rendering; dagre computes node positions, reactflow renders/pans/zooms them) with a **client-side** "Show subtopics" toggle (default off, same rationale as `includeClos`) -- BIO-G9's full graph is 137 nodes, which `fitView` renders illegibly small; hiding subtopics by default (52 nodes) keeps the initial view readable, with pan/zoom (via reactflow's built-in controls + minimap) for exploring further. Verified in a real browser against live BIO-G9 data: rendered node/edge counts matched the API response exactly at every toggle state (52/73 without subtopics, 137/158 with, 214+ with CLOs), zero console errors, and a zoomed-in screenshot confirmed node labels, color-coding (subject/unit/topic/external), and prerequisite edges (e.g. "Diseases" → "Bacteria (G12, BIO-G12)") all render correctly, not just that the library mounted.
- **Ethiopian MoE Biology G7-G12 curriculum, fully ingested** (2026-08-10) — real production content, not seed/demo data: 6 subjects (`BIO-G7`...`BIO-G12`), 33 units, 109 top-level topics + 445 subtopics (554 total), 806 CLOs, 4,593 topic-CLO mappings, and **90 explicit cross-grade prerequisite edges** (`infer_method='moe_document'`, auto-validated, all Neo4j-synced) — sourced from a pre-structured source document (`EduGraph_Biology_G7_G12_Unified.docx`, an already-ID-tagged "Unified Structured Extraction for Knowledge-Graph Ingestion," not a raw curriculum PDF) via a dedicated deterministic parser rather than the AI/heuristic `curriculum_worker` pipeline (which is built for messy raw PDFs and would've done worse here). Tooling: `backend/cmd/ingest-biology/main.go` (a real, reusable one-off importer — reads a pre-parsed JSON, calls `Repository.ApproveAndPromote` and `Service.AddTopicPrerequisite` in-process per grade, no HTTP round-trips) plus two Python scripts (not checked into this repo — ran from a scratch directory) that parsed the source `.docx` deterministically off its own ID convention and reshaped the result into the JSON shape `ingest-biology` expects. Local Neo4j was fully wiped (`MATCH (n) DETACH DELETE n`) before ingesting, at the user's explicit request, for a clean rebuild. Unit-level prerequisite statements (e.g. "G7.U2 REQUIRES G7.U1") were anchored to specific topics per an explicit decision: first topic of the dependent unit → last topic of the prerequisite unit, rather than fabricating a cross-product of every topic pair or skipping them. Verified post-ingest: Postgres and Neo4j node/relationship counts match exactly (554 `HAS_TOPIC`, 445 `HAS_SUBTOPIC`, 4,593 `HAS_CLO`, 90 `HAS_PREREQUISITE`), and content spot-checks (e.g. G9's "The Cell" topic: 4 subtopics + 12 CLOs = 5 topic-level + 7 unit-level, exactly matching the source) confirm fidelity, not just counts.

## What's Built — Production Curriculum Upload/Extraction: "Unified ID Convention" Format (2026-08-11)

The real curriculum upload/parse pipeline (`POST /api/v1/curriculum/upload` → `curriculum_worker`), not just the one-off `ingest-biology` bypass, now correctly parses the "Unified ID Convention" document format that `EduGraph_Biology_G7_G12_Unified.{pdf,docx}` and future MoE source documents of the same shape use — dot-separated IDs (`G{grade}.U{unit}.T{topic}.{subtopic}`), `Unit CLOs (...)`/`Subtopics (...)`/`Topic/Subtopic CLOs (...)`/`Assessment (...)` section markers.

- **`ai-service/app/services/curriculum_parser/id_convention.py`** (new, shared by both extractors) — format-agnostic: takes a plain text blob, detects the convention (`looks_like_id_convention`), and state-machine-parses it into the same dict shape (`sequenceOrder`, `titleEn`, `keyConcepts`, `learningOutcomes`, `clos`, `rawText`, `externalCode`, `subtopics`) the Go `dto.ParsedTopic`/`ParsedUnit` expect, so round-tripping through `POST /curriculum/jobs/{id}/approve` works unchanged.
- **`extractor.py` (PDF)** and **`docx_extractor.py` (DOCX)** each gained a "Strategy 0" check at the top of `extract_structure()`: if the document's full text matches the ID convention, delegate to `id_convention.extract_grade()` instead of the TOC/font-heuristic fallback (which is built for messy raw curricula and does worse on a document that already carries structured IDs).
- **PDF-specific defects found and fixed**, all via cross-checking against the known-correct DOCX-derived counts (per-grade units/topics/subtopics/topicCLOs/unitCLOs) rather than trusting output at face value: `rpartition` instead of `partition` on `"PART II"` (appears twice — TOC entry + real section — truncating the doc to nearly nothing); trailing bullet glyphs glued onto chunk ends breaking exact-match header regexes; PDF line-wrap hyphenation splitting words across raw newlines (fixed pre-whitespace-collapse); the "Topic/Subtopic CLOs" marker itself wrapping across a raw newline in the PDF (fixed by using `\s+` instead of literal spaces in every multi-word marker pattern); page-footer numbers landing immediately after a header when it's the last thing on its page (fixed with an optional trailing-page-number tolerance scoped only to header regexes, never to free-text body regexes, so a real description ending in a number is never truncated).
- **Verified**: exact match on all 6 grades against both the real PDF and real DOCX (units/topics/subtopics/topicCLOs/unitCLOs counts), zero leaked-marker issues in a final scan, dehyphenation spot-checked correct. ### New finding: `ApproveAndPromote` is slow over Supabase for a full grade, and the Vite dev proxy hides it as a false 500

Approving the throwaway grade-7 test job (95 topics/subtopics, 138 CLO codes) took **198 seconds** server-side (confirmed via `docker compose logs api`, eventual `200`) — but the browser saw the request fail with a **500 and empty body** well before that, because the Vite dev-server proxy times out and returns its own error to the client while the Go request keeps running server-side to completion. The backend write was correct (verified via direct count checks in both Postgres and Neo4j after the fact), so this is not a data-correctness bug — it's a **latency regression from the Supabase migration**: `ApproveAndPromote`'s per-topic/per-subtopic/per-CLO upserts and the subsequent per-node `syncCurriculumGraph` Neo4j `MERGE` calls were fine as sequential round-trips against a near-zero-latency local Postgres container, but now each round-trip pays real network latency to the Supabase pooler (`aws-0-eu-central-1`), and a full grade means on the order of a few hundred sequential round-trips. **Not yet fixed** — the real fix is batching `ApproveAndPromote`'s inserts (multi-row `INSERT ... VALUES (...), (...)` or `COPY`-style bulk upsert instead of one row at a time) and/or raising the Vite proxy timeout so at least the UI reflects the true state instead of a misleading failure. This will affect approving any of the other real `BIO-G8`..`BIO-G12` subjects (already done via `ingest-biology`, which bypasses HTTP entirely and isn't affected) and any future curriculum officer's real upload through the UI for a similarly large subject.

## What's Built — EG-GCKT: Graph-Cognitive Knowledge Tracing (2026-08-15)

A 12-milestone implementation of `EduGraph_EG-GCKT_Professional_Model_Specification.docx.pdf` (a 24-section research-grade learner-modeling spec), built in one session on explicit authorization to modify existing gap-analysis/study-plan code broadly. Plan at the time is preserved in that session's transcript; this section is the durable record. **Everything below compiles/imports/type-checks (`go build ./... && go vet ./...`, `python -c "import app.main"` with all 8 workers wired, `npm run type-check && npm run lint`) — none of it has been exercised against a running Docker stack or a real browser yet**, unlike the curriculum/prerequisite features documented elsewhere in this file with Playwright verification. Treat it as implemented-and-self-consistent, not yet end-to-end-verified.

- **Foundation schema** (migrations V033-V042) — `curriculum.topic_prerequisites` gained typed edges (`edge_type` — `requires`/`strongly_requires`/`recommended_before`/`related_to`/`similar_to`/`supports`/`alternative_to` — plus `confidence`/`evidence`/`created_by_model`/`curriculum_version`; existing rows backfilled `edge_type='requires'`; unique constraint widened to `(topic_id, prerequisite_id, edge_type)`); cycle detection and the class-heatmap cross-grade walk (`class_heatmap.go`) now filter to `requires`/`strongly_requires` only. New `assessment.item_skill_mappings` — a real versioned Q-matrix (relevance, cognitive level, difficulty/discrimination once calibrated, generation method, version/is_current/superseded_at), backfilled from every pre-existing `questions.topic_id`/`clo_code` pointer, leaving `questions.topic_id` itself untouched as the fast single-skill pointer other code still reads. New `modeling` Postgres schema: `model_snapshots` (one generic candidate/validated/active/rejected/superseded governance table every engine's parameters flow through) and `evidence_log` (append-only `Evidence = {estimate, uncertainty, recency, sample_size, reliability, provenance, context, model_snapshot_id}` objects). New `students.skill_states` (the Student Knowledge State Graph — a per-student overlay on `curriculum.topics`, **cold start via row absence, never a fabricated 0.0**: no row exists until the first evidence arrives). New append-only `students.learning_events` (written synchronously by Go inside `RecomputeAttemptTotals`, the same seam that already pushes `queue:gap:analyze` — a second Redis list, `queue:gckt:trace`, is pushed alongside it, deliberately separate so `BRPOP` on one queue can never starve the other's consumer). New `curriculum.prerequisite_review_history` / `assessment.item_skill_mapping_review_history` / `curriculum.node_review_history` (append-only audit trails, mirroring the one real precedent already in this schema, `assessment.answer_grade_history`). New `students.misconception_hypotheses` and `students.recommendation_log`. All School-Box-local new tables got `sync.outbox` triggers (V040) alongside the existing set.
- **BKT / DINA / IRT analytical engines** (`ai-service/app/services/knowledge_tracing/{bkt,dina,irt}.py`) — real math, not fabricated: standard 4-parameter Bayesian Knowledge Tracing (online, per-response, forward-pass updates); DINA joint posterior over the small per-item attribute space (deterministic-input-noisy-AND), not a full whole-exam joint model; 2PL IRT ability estimation via Newton-Raphson MLE. **All three run on honest population-default/CTT-proxy parameters** (this system has ~zero real student interaction data — confirmed during planning: demo seed has 0 exam answers, the only bulk generator is a disposable k6 load-test fixture with degenerate single-question answers) and all three are scope-aware: each checks for a per-skill/per-item `active` `model_snapshots` row before falling back to the global default, so a promoted refit (see below) takes effect automatically. Dispatched per graded attempt from `ai-service/app/workers/kt_worker.py` (BRPOP on `queue:gckt:trace`).
- **Graph-Cognitive State Fusion Engine** (`ai-service/app/services/knowledge_tracing/fusion.py`) — combines every unconsumed `evidence_log` row for a (student, topic) into one `skill_states` estimate, weighted by `reliability × recency_decay × sample_size_factor`; disagreement between sources widens fused uncertainty rather than averaging it away; graph-reasoning evidence is deliberately the lowest-weighted source (spec's critical safeguard: structural context informs, never overrides, observed evidence). Supports an `excluded_provenances` ablation parameter (used by the evaluation harness, see below).
- **Root-cause diagnosis + consistency checking** (`ai-service/app/services/gap_analysis/{root_cause,consistency}.py`) — replaces the old "deepest weak prerequisite" heuristic in gap-analysis Pass 2 with the spec's actual Root Cause Score (`Weakness × EvidenceConfidence × DownstreamImpact × PrerequisiteReadiness × InterventionGain`); reproduces the spec's own Fractions worked example (a numerically-weaker downstream symptom correctly loses to the upstream topic that actually explains it). `consistency.py` detects a strong topic with an evidenced-weak direct prerequisite, and — only when both sides are well-evidenced, not sparse — penalizes that prerequisite edge's `confidence` and logs why to `prerequisite_review_history`: the "graph becomes an active diagnostic instrument" loop, teacher-mediated rather than a fully automated closed-loop item-delivery system (that's out of scope, documented as such).
- **Misconception modeling** (`ai-service/app/services/gap_analysis/misconception.py`, `students.misconception_hypotheses`) — when an attempt shows ≥2 missed questions on the same symptom topic, one LLM call (via the existing `llm_provider.py` local-first abstraction) proposes a structured candidate misconception; always inserted `status='candidate'`, never auto-confirmed. Teacher review: `PATCH /api/v1/misconceptions/{id}/review` (`backend/internal/assessment/{dto,repository,service,handler}/misconceptions.go`) confirms/rejects; a confirmed hypothesis folds into the owning `skill_states.misconception_state` JSONB.
- **Next-best-action ranking** (`ai-service/app/services/study_plan/action_ranking.py`) — replaces `study_plan/service.py`'s severity-only tie-break (within the unchanged Kahn's-algorithm topological structure) with a 6-factor composite score: expected learning gain, information gain (favors high-uncertainty topics), prerequisite impact, forgetting/recency need, mandatory-CLO curriculum priority, and a repetition penalty (`students.recommendation_log`, new — nothing previously recorded that a topic had already been suggested).
- **Governance: nightly refit + review UI** (`ai-service/app/workers/refit_worker.py`, `backend/internal/modeling/`) — a Python asyncio periodic loop (the first time-based ai-service worker; every other one is a Redis consumer) mirroring the Go `qualityworker` pattern's shape (no Celery, embedded in the running process). Refits BKT/DINA/IRT parameters via coarse grid-search MLE once a skill/item crosses 30 observations; **always writes a `candidate` snapshot, never activates one automatically**. Review queue at `GET /api/v1/model-snapshots/candidates` + promote/reject endpoints (ministry_admin), frontend at `/model-governance` (`frontend/src/features/modeling/ModelGovernancePage.tsx`). Promoting supersedes (not deletes) the prior active snapshot, so re-promoting an older one is how a bad refit gets rolled back.
- **Evaluation / ablation harness** (`ai-service/app/services/evaluation/{metrics,harness}.py`) — real AUC (Mann-Whitney U), log loss, Brier score, and expected calibration error, no sklearn dependency. `harness.py` runs a **prequential (forward-chaining) evaluation**: a variant's prediction for a response may only use evidence strictly predating that response, enforced as the one non-negotiable rule in the module (anything else would be circular). Baselines: frequency, bkt-only, dina-only, irt-only, graph-only heuristic, full_gcsf. Every result honestly reports `insufficient_data` below a coverage threshold rather than fabricating a benchmark number — expected on most dimensions until real usage volume exists. Runnable directly: `python -m app.services.evaluation.harness`.
- **Explainability** (`GET /api/v1/students/{id}/topics/{topicId}/explain`, `backend/internal/modeling/{dto,repository,service,handler}/explain.go`) — the spec's five-part explanation (current state, evidence, structural context, confidence, recommendation + reason) read directly from Postgres, no live ai-service call. **Caught and fixed an IDOR during implementation**: `studentID` is a caller-supplied path param, so `Service.authorizeExplain` enforces ownership server-side (a student may only view their own explanation; a teacher/school_admin only a same-school student; ministry_admin/regional_admin/curriculum_officer unrestricted) — the same class of bug this codebase's career-matches endpoint had before checklist 11.3's fix, caught this time before shipping rather than after. Frontend viewer at `/students/:id/topics/:topicId/explain` (`frontend/src/features/modeling/ExplainPage.tsx`) — a standalone, directly-linkable page; it was **not** wired as a click-through panel into the existing class-heatmap or exam-insight pages (heatmap is class-aggregated with no single-student context to link from; exam-insight integration was left for a follow-up session rather than risking a late, unreviewed edit to those existing pages).
- **Prerequisite/Q-matrix editing UI** (`frontend/src/features/curriculum/PrerequisitesPage.tsx`) — extended with the edge-type selector (7 types) and confidence/evidence fields on the add-link form, plus a per-edge "History" panel reading `GET /curriculum/topics/:id/prerequisites/:prereqId/history`.

**Deliberately not built, not silently skipped**: DKT and true MIRT calibration. The spec's own Phase 6 defers DKT to "where justified by data" — this system doesn't have that data yet (see above), and building either would mean fabricating results with no real statistical basis, which the spec's own Design Principles explicitly reject ("say unknown rather than manufacture confidence"). `modeling.model_snapshots.model_type` reserves `dkt_model`/`mirt_calibration` for when real usage volume justifies building them — no code exists for either beyond that reserved enum value.

### EG-GCKT checklist gap-closing pass (2026-08-15, migrations V043-V049)

A follow-up pass cross-referencing a separate ~300-item implementation checklist against the 12-milestone build above; each item below closes a real, verified gap (100 Python tests, `go build ./... && go vet ./...`, `npm run type-check && npm run lint` all passing), not a restatement of what the original milestones already covered.

- **Blocked-Learning & Recovery System** (checklist section 13; `students.recovery_attempts` V044, `ai-service/app/services/gap_analysis/recovery.py`) — detects 3 consecutive incorrect responses on a topic (`is_blocked`), routes through `similar_to`/`alternative_to`/lower-granularity-subtopic/`related_to` edges in that priority order, tracks attempt outcomes, and escalates to `teacher_escalation` after `TEACHER_ESCALATION_FAILED_ROUTES=2` failed automated routes. Wired into `kt_worker.py` after every graded attempt.
- **Root Cause Score persistence** (V043) — `students.gap_records` gained `rcs_score`/`rcs_factors`/`root_cause_path` JSONB columns so the score `root_cause.score_candidates()` was already computing is actually stored and readable (`/exams/{id}/my-insight` etc.), not recomputed-and-discarded per request.
- **`fusion_policy`/`recommendation_policy` versioning** (checklist section 18: "version recommendation policy") — both now write/read an `active` `modeling.model_snapshots` row (`fusion.py`'s `_get_fusion_policy_snapshot_id`, `action_ranking.get_recommendation_policy_snapshot_id`) instead of being hardcoded constants with no audit trail.
- **Graph-reasoning evidence producer** (`root_cause.produce_graph_evidence`) — graph-reasoning was a reliability weight in the fusion formula with nothing ever writing that provenance to `evidence_log`; now `kt_worker.py` calls it per topic before fusion runs, so the lowest-weighted-but-real evidence source actually exists.
- **`skill_states.structural_status`** (V045) — `fusion._compute_structural_status` computes `prerequisitesSatisfied`/`weakPrerequisiteCount`/`blocked`/`activeRecoveryRouteTopicId` and stores it alongside the fused mastery estimate; previously `upsert_skill_state` always received `structural_status=None`.
- **Misconception verification-item assignment** (`misconception.select_verification_item`, `check_verification_responses`) — a candidate hypothesis now gets a `verification_item_id` at generation time, and a later correct/incorrect response on that specific item nudges the hypothesis's `confidence` (`VERIFICATION_CORRECT_DELTA=-0.15`/`VERIFICATION_INCORRECT_DELTA=0.1`) instead of confidence being static after creation.
- **Q-matrix / prerequisite quality reports** (`GET /curriculum/subjects/{code}/qmatrix-quality`, `.../prerequisite-quality`; `curriculum/{dto,repository,service,handler}/quality_reports.go`) — surfaces items with missing/low-confidence skill mappings, ambiguous multi-topic mappings, orphaned topics (no prerequisite edges at all), and low-confidence prerequisite edges, for a curriculum officer to triage.
- **Distinct next-best-action action types + IRT difficulty-fit** (`action_ranking.classify_action_types`, checklist section 14) — replaces the "everything is `practice`" placeholder with `practice`/`diagnostic`/`concept_explanation`/`alternative_representation`/`prerequisite_review`/`spaced_review`/`teacher_escalation`, and wires Milestone 8's IRT `p_correct` into a real `WEIGHT_DIFFICULTY_FIT` ranking factor (was deferred pending IRT existing — it now does).
- **`no_fusion` evaluation baseline** — `evaluation/harness.py`'s `VARIANTS` gained a variant that skips the fusion engine entirely (each source's raw estimate), so the harness can report whether fusion is actually adding predictive value once real data exists, not just compare single-source variants against each other.
- **Learner-state snapshots + replay** (checklist sections 6/18/22; V047, `students.skill_state_snapshots`; `ai-service/app/services/knowledge_tracing/{replay,snapshot}.py`) — `refit_worker.run_once()` takes a nightly point-in-time snapshot of every (student, topic)'s fused state via `take_all_snapshots`; `replay.py` (extracted from the evaluation harness's prior duplicate `_prior_evidence`/`_fuse_point_in_time`) is the one shared point-in-time-fusion-reconstruction implementation used by both the harness and the snapshot worker — `fusion.py`'s live path stays intentionally separate since it has production side effects (`consumed_by_fusion_at` mutation) a backtest/snapshot must never trigger. `GET /students/{id}/topics/{topicId}/state-snapshots` (`backend/internal/modeling/.../snapshots.go`, reuses `authorizeExplain`'s IDOR-safe ownership check); rendered as a "History" panel on `ExplainPage.tsx`.
- **Recommendation outcome / feedback-loop tracking** (checklist sections 2/14/20: "measure learning gain" / "capture action outcome"; V049) — `students.recommendation_log` gained `mastery_at_recommendation`/`evidence_count_at_recommendation` (captured at `log_recommendations` time from the then-current `skill_states` row, NULL for a genuine cold start — no fabricated baseline) and `outcome_status`/`mastery_at_evaluation`/`outcome_evaluated_at`. `refit_worker.evaluate_recommendation_outcomes()` runs nightly alongside the parameter refits: rows pending ≥7 days get classified `improved`/`worsened`/`unchanged`/`insufficient_evidence` (`_classify_outcome`, pure and unit-tested) by comparing the baseline to the current `skill_states` row. This is what makes it an actual **feedback loop**, not just a log: `postgres_studyplan.fetch_repetition_counts` now weights past recommendations by their measured outcome (a `worsened` repeat penalizes 2×, an `improved` one only 0.5×) instead of a flat per-occurrence count, so the next plan generation's repetition penalty is outcome-aware.
- **Bug found and fixed during this pass**: `action_ranking.classify_action_types` has assigned `teacher_escalation` since the checklist-section-14 work above, but V042's original CHECK constraint on `students.recommendation_log.action_type` never included that value — every teacher-escalation recommendation would have failed to insert with a constraint violation. Fixed in V048 (widened CHECK), caught by cross-checking the Python enum against the Postgres schema rather than by a failing test (nothing in the existing suite exercised this path against a real constraint).

**Explicitly deferred from this pass, not silently dropped** (same "documented, not built" standard as DKT/MIRT above): full curriculum hierarchy rewrite (Concept/Skill/Learning-Objective/Assessment-Objective as distinct graph nodes, rather than the current Topic-only granularity) — a schema-level redesign out of proportion to the gap it closes; assessment item (`questions`) versioning — no evidence yet that items are edited post-publication often enough to need it; full MLOps/monitoring dashboards (Prometheus/Grafana drift alerting for the KT engines) — contradicts this project's own "don't build unused production infra" principle when Grafana/Prometheus are already present-but-unused in `docker-compose.yml`; cohort-level fairness/calibration monitoring — no demographic data model exists to condition on; root-cause/Q-matrix/recommendation-quality evaluation against expert-labeled ground truth — blocked on not having any labeled data, same reasoning as the DKT deferral; closed-loop automated diagnostic-item delivery for consistency verification — Milestone 5 already ships detection + teacher-mediated resolution, and full adaptive-testing delivery is its own project.

## Database Structure

**Postgres** (verified live on Supabase as of 2026-08-10 — see "Postgres is now Supabase" above; not the aspirational 14-schema design in `edugraph-db-design.docx`) — actual schemas: `public` (users, schools, regions, students, teachers, jobs, notifications, refresh_tokens, sync_logs), `curriculum` (upload_jobs, subjects, units, topics, clos, topic_clo_mappings, topic_prerequisites — gained typed edges V033; prerequisite_review_history — V033; node_review_history — V036), `app_storage` (local_files — BYTEA dev storage; named `app_storage` rather than `storage` specifically to avoid colliding with Supabase's own Storage-product schema of that name), `assessment` (exams, questions, question_options, student_answers, exam_quality_reports — V017-V024; item_skill_mappings + item_skill_mapping_review_history — the real versioned Q-matrix, V034/V035), `careers` (career_paths, career_matches), `embeddings` (clo_embeddings, topic_embeddings — written on every curriculum approval as of V025/2026-08-10, stub model only, see "CLO/Topic Embeddings" above; question_embeddings — still provisioned, unused), `students` (gap_records, exam_insights, subject_profiles, study_plans — V023; skill_states, learning_events, misconception_hypotheses, recommendation_log — EG-GCKT, V037-V042), `schools` (quality_scores — V024, a **separate schema** from the `public.schools` table, easy to confuse), `modeling` (model_snapshots, evidence_log — EG-GCKT governance backbone, V037). No RLS, no per-schema partitioning. pgvector is now used (embeddings.clo_embeddings/topic_embeddings, HNSW cosine indexes) but only by the stub provider — the `careers.embedding`/`curriculum.clos.embedding` `vector(1024)` columns and `embeddings.question_embeddings` remain unused.

Key tables:
- `curriculum.upload_jobs` — `status` progresses `pending → parsing → parsed → review → approved | rejected | failed`; `file_s3_key` holds the Postgres `storage.local_files` UUID in dev mode (name is legacy from the S3-first design); `parsed_structure` JSONB holds the AI-extracted tree; `neo4j_written` flags whether the graph mirror succeeded.
- `curriculum.subjects` (versioning columns added V025) — `version`/`is_current`/`superseded_at`/`previous_version_code` track mid-year revision lineage; a revision is a new subject row under a new `code`, linked via `POST /curriculum/subjects/{code}/supersede`, never an in-place overwrite of an existing row.
- `students.gap_records` / `students.exam_insights` / `students.subject_profiles` (V023) — output of the gap-analysis 3-pass pipeline; `gap_records` also drives the class heatmap and study-plan generation.
- `students.study_plans` (V023) — one active plan per (student, target); day-by-day blocks with a "why" derived from gap root causes + prerequisite ordering.
- `assessment.exam_quality_reports` / `schools.quality_scores` (V024) — recomputed on read, not write-through; `schools.quality_scores` has a Redis cache layer (`school_quality:{schoolId}`, TTL 1h).
- `students.skill_states` (V037, EG-GCKT) — the fused per-student learner state (mastery_probability/uncertainty/trend/evidence_count/forgetting_risk/misconception_state), written by `ai-service`'s fusion engine; a row only exists once evidence has arrived for that (student, topic) pair, never pre-created.
- `students.learning_events` (V038, EG-GCKT) — append-only raw response log (skill_ids, correctness, response_time), one row per graded answer, immutable/write-once by design (distinct from the mutable `assessment.student_answers`).
- `modeling.model_snapshots` / `modeling.evidence_log` (V037, EG-GCKT) — versioned parameters for every BKT/DINA/IRT/(reserved DKT/MIRT) engine with a candidate/validated/active/rejected/superseded lifecycle, and the append-only evidence objects the fusion engine consumes.
- `curriculum.topic_prerequisites` (typed edges added V033) — `edge_type` now distinguishes hard dependencies (`requires`/`strongly_requires`, cycle-checked) from soft associations (`related_to`/`similar_to`/`supports`/`alternative_to`/`recommended_before`); `confidence`/`evidence` are separate from the pre-existing `weight` column.
- `assessment.item_skill_mappings` (V034/V035, EG-GCKT) — the real versioned Q-matrix; `questions.topic_id`/`clo_code` remain the fast single-skill pointer other code reads, untouched.

**Neo4j** — actual node/relationship types in use: `(:Subject)-[:HAS_UNIT]->(:Unit)-[:HAS_TOPIC]->(:Topic)`, `(:Topic)-[:HAS_PREREQUISITE]->(:Topic)`, `(:School)-[:ENROLLS]->(:Student)-[:STRUGGLED_WITH {severity,isRootCause}]->(:Topic)`, `(:Teacher)-[:TEACHES_AT]->(:School)`. CLO nodes are the one planning-doc structure still not mirrored (deliberately, Phase 2 scope).

**Redis** — six queues in active use, all plain-string job-id (or JSON payload) lists via `LPUSH`/`BRPOP`, no Celery protocol: `queue:curriculum:parse`, `queue:exam:parse`, `queue:exam:answerkey`, `queue:gap:analyze`, `queue:studyplan:generate`, `queue:gckt:trace` (EG-GCKT, 2026-08-15 — pushed alongside `queue:gap:analyze` at the same exam-finalize seam, kept as a separate list so one queue's `BRPOP` consumer can never starve the other's) (`ai-service/app/db/redis.py`). Also used for refresh-token storage (`internal/auth`) and a 1h school-quality-score cache.

Roles (Postgres `users.role`, enforced via Go `RequireRole` middleware — not Postgres RLS): `student`, `teacher`, `school_admin`, `regional_admin`, `ministry_admin`, `curriculum_officer`. Seed demo users exist per `V015__seed_demo_data.sql`, e.g. `curriculum.officer@edugraph.et` / `student@edugraph.et` / `teacher@edugraph.et`, all `password123`. Login response uses snake_case `access_token`.

## Development Rules

- **Local dev**: `docker compose up -d` (Postgres is Supabase now, not a compose service — see "Postgres is now Supabase" above). If containers already exist from a prior session, `docker compose up -d --force-recreate <service>` after editing `docker-compose.yml` — env var changes don't apply to a running container, only a recreate.
- **Migrations**: Flyway naming `V{n}__{description}.sql` in `backend/db/migrations/`, strictly sequential, never edit a merged migration — add a new one. Never `DROP` a column; additive only. Run against Supabase with `docker run --rm -e FLYWAY_URL=... -e FLYWAY_USER=... -e FLYWAY_PASSWORD=... -v "<abs-path-to>/backend/db/migrations:/flyway/sql" flyway/flyway:10 -locations=filesystem:/flyway/sql migrate` (standalone, not the compose `flyway` service, which now only targets the local-fallback Postgres) — use the pooler URL/user from `.env`, and prefer PowerShell over Git Bash for the volume mount (MSYS path translation mangles the repo's spaced directory name).
- **Auth**: RS256 JWT, 15-min access / 7-day refresh (single-use, rotated on `/auth/refresh`). Dev keypair auto-generated by `crypto.EnsureDevKeyPair` when `APP_ENV=development` — never commit real keys.
- **File uploads**: validate by magic bytes server-side, never trust `Content-Type`. See `sniffCurriculumMime` in `backend/internal/curriculum/handler/handler.go`.
- **Frontend**: `npm run type-check`, `npm run lint`, `npm run build` must all pass clean before considering frontend work done — `node_modules` and several config files (`tsconfig.node.json`, `.eslintrc.cjs`, `postcss.config.js`, `vite.config.ts`, etc.) have previously been found as **empty stub files** despite looking present; verify they have real content before assuming the scaffold works.
- **Don't build unused production infra.** Kong, Kubernetes, HashiCorp Vault, MFA, ElectricSQL, Istio — all described in `edugraph-architecture.docx` — do not exist in this repo and there's no cloud account to run them against. Treat that doc as a security/design checklist to mine for concrete hardening (e.g. bcrypt cost, magic-byte validation), not a build target, unless explicitly asked to provision real infra.
- **Reading the `EduGraph AI/*.docx` planning docs**: they're binary — use `python-docx` (`import docx; docx.Document(path)`) to extract text, or let `graphify` convert them (`graphifyy[office]` extra required — without it they're silently skipped).

## Critical Decisions

- **Dual-storage adapter over direct S3** (`Untitled document.docx`): deliberate choice to develop against Postgres BYTEA locally with a swappable `StorageProvider` interface, so production S3 support is a one-file addition later, not a rewrite.
- **BRPOP consumer, not Celery**, for the curriculum worker — the Go producer pushes a raw string via `LPUSH`, incompatible with Celery's message protocol; documented inline in `curriculum_worker.py`.
- **CLO Neo4j sync deferred to Phase 2** — `ApproveAndPromote` only mirrors Subject/Unit/Topic; this is intentional scope, not a bug (matches the commit history and `edugraph-impl-plan.docx`'s phase ordering).
- **bcrypt cost 12** (not the Go default of 10) and **magic-byte file validation** (not `Content-Type` header) were hardened deliberately against `edugraph-architecture.docx`'s stated minimums — both are real, currently-enforced controls, not aspirational.
- **Frontend was empty scaffolding until 2026-07-17** — full tooling was present (React, TanStack Router/Query, Zustand, Tailwind, Radix, etc.) but zero implementation existed; login/upload/review pages were built from scratch that session. If frontend files look suspiciously sparse, check file size before assuming they're implemented.
- **`docker-compose.yml`'s `VITE_API_URL`/`VITE_AI_URL` previously pointed at the AI service instead of the Go API** — fixed to a Vite dev-server proxy pattern (`API_PROXY_TARGET`, resolved per-environment in `vite.config.ts`) so the frontend always reaches the Go API regardless of whether it's running via `npm run dev` or inside Docker Compose.
